# Release notes

Internal, release-by-release log of the planner and the club manager pivot. The public README keeps only the product overview.

## 3.5 — small-sided playable practice

New three-a-side drills now use a separate v3 engine: a physical 60×40m field with a roughly 4.3m goal mouth, two 90-second halves, nearby support triangles, one pressing outfielder and one covering outfielder. Keepers defend the smaller goal/area. Each side remains three players; substitutes are not introduced and free drills do not inflict injury attrition. No offside in this practice format. Player movement, contact, ball speed, passing and shooting retain metre-based ability effects rather than shrinking character/ball motion with the visual field. The small-sided camera, 3D field/goals and tactical coordinate mapping agree with simulation dimensions.

The lab displays remaining time and touches/passing/tackles/goals, supports a half-time continuation and an explicit Play again action after full time. Attack direction changes at half time. Goalkeeper previews now honour the selected planner position. New practice uses v3; solo, fixed-seed attribute trials and the passing-gate challenge retain v2. Formal fixtures still use immutable v1 with five-minute halves. The v2 and v3 engine sources are retained in the engine contract. Existing local practice checkpoints can resume under their own engine; merely opening a new paused preview no longer overwrites the older checkpoint. Storage IDs, data version 8 and the private production database are unchanged.

Validation: 276 automated tests, typecheck, four SQLite migration checks and official build. Tests cover six-player bounds, goal and throw-in lines, nearby support, full two-half simulation, no extra substitutions, exact checkpoint continuation, low-rating movement, goalkeeper setup and retained v2 dispatch. Isolated browser QA exercised keyboard movement and charged passing with moving opponents, 390px English/Chinese/tactical/3D layouts, blur pause and refresh recovery. Synthetic near-boundary states checked half-time, full-time and restart UI; the full simulation is separately exercised by automated tests. A populated v2 local checkpoint remained unchanged while the new preview sat idle, then resumed at its original frame. No real school statuses, formal fixtures, XP, coins or inventory were changed. Physical phone FPS, measured input latency and the broader match-feel acceptance gate remain open; this release advances plan stage ② and does not claim a finished competitive-engine upgrade or housing delivery.

## 3.7 — responsive practice (`fixed-football-4`)

Free three-a-side practice now creates a new simulation version, `fixed-football-4` / `pitch-physics-4`, on the same 60×40 practice field. Published v1, v2 and v3 remain immutable: saved competitive matches, replays and older practice checkpoints still dispatch to the engine version recorded with them, and `.openai/football-engine-contract.json` freezes the new file hash without changing the earlier entries. Solo ball work and the passing-gate challenge keep their v2 engine.

The engine adds a one-slot buffered first touch for the controlled player: an action pressed while a pass is genuinely travelling (loose ball, within 9 m) is stored with its power, aim and held direction, then released as a real one-touch when the ball arrives; the direction becomes the first touch. The window is 0.55 s on arrival and buffers older than 0.6 s are discarded, so a stale press can never fire late, and pressing while a teammate carries the ball still means "ask for the ball". The simulation also publishes `passPreview` — the same deterministic recipient the release would choose — so the pitch can mark the current carrier (amber ring and pole) and the pass target (lime ring, pole and marker) in 3D and in tactical view, with an attack-direction arrow. Defending keeps shape: the nearest opponent presses, the second covers between ball and goal, and the rest hold their formation slot with the block shifting toward the ball instead of all collapsing onto one threat; support runners keep separate channels.

The lab accepts v4 checkpoints after reload, clears held keys and sends a zeroed movement/sprint/close-control/shield input when resuming, and "Play again" deletes the stored checkpoint rather than resurrecting the old drill. Practice still awards no XP, credits, fixture passes or career results, and no schema, migration or production record changed.

Validation: 312 automated tests (six new v4 cases covering dispatch and field size, pass-preview stability and clearing, a real buffered one-touch, stale-buffer expiry, measured slot-shape drift against retained v3, and a deterministic v4 checkpoint round trip), typecheck, four SQLite migration checks and the official release-contract check. Isolated local browser QA with a synthetic owner observed the v4 engine in the live HUD, a `fixed-football-4`/`pitch-physics-4` local checkpoint, published carrier and pass target while playing, the buffer flag set during a pass flight and cleared afterwards, a v4 checkpoint resumed after reload, 60 FPS in a short 1440×960 headless sample, and a 390×844 viewport without overflow. Physical-phone frame rate, thermal behaviour, measured input latency and the full match-feel acceptance gate remain unverified; 11-a-side, substitutes and competitive fixtures are unchanged.

## 3.11 — offline copy and queued changes

The private site keeps a device-only copy of the planner and lets a signed-in device keep working when the connection drops. A second IndexedDB database (`questbound-site`) stores the last server-accepted envelope and a queue of commands with their original operation ids; an older revision can never overwrite a newer copy. `lib/site-queue.ts` holds the pure rules: append without duplicating an id, replay the queue over the last server copy so the change is visible without touching the server revision, send in order, refresh and retry once on a stale revision, keep everything on a real conflict, and stop at the first network failure without dropping the rest.

When a navigation fails, `public/sw.js` answers with a self-contained offline page (no framework hydration) that reads the same device copy: last save time and revision, how many changes are waiting, the next open tasks with a **Done** button that queues a real completion, bilingual copy following the saved language, and an automatic reload when the connection returns. Private pages and `/api/*` are still never cached; Cache Storage holds only the shell and static assets. In the app, a failed load falls back to the snapshot ("Local saved"), a command with no HTTP answer is applied locally and queued instead of pretending to be saved, and reconnecting (`online`, the next load, or the 30-second poll) replays the queue and replaces the local view with the authoritative state; a conflict keeps the change on the device for review.

Validation: typecheck, 332 automated tests (11 new: queue order/dedupe, local replay, newest-snapshot rule, ordered send, one 409 refresh-and-retry, conflict retention, stop-on-failure, IndexedDB snapshot/queue durability, older-revision rejection, dedupe and clear), four SQLite migration checks, `npm run prebuild` and a production build that emits `/offline` as a static route. Browser end-to-end with a synthetic local owner: the worker controls the page with one shell cache, the device snapshot is written, an offline completion reports `本机已保存` and queues one operation, an offline reload serves the copy page with "1 项修改已保存在本机", a second completion from that page raises the queue to 2, and reconnecting flushes both (queue 0, the server's completed-task count rose from 9 to 11). Offline you get the copy page rather than the full planner UI, replay is foreground only, and rewards remain server-confirmed. A follow-up cache-correctness fix makes the worker store a response only when its content-type matches the request (stylesheets as text/css, scripts as javascript) and moved the cache to `qfc-shell-v2`, after a QA finding that dev CSS could be cached under a JavaScript MIME and leave the app unstyled; a fresh-context check confirms all stylesheets parse with the worker in control. Physical-phone offline behaviour and cache eviction limits remain unverified.

## 3.70 — match engine v2: possession chains, xG and a carrier timeline

The manager match now runs on a second engine (`lib/match-v2.ts`) that every new quick simulation **and** every new live match share. Open-source football sims and analytics informed the design: [GallagherAiden/footballSimulationEngine](https://github.com/GallagherAiden/footballSimulationEngine) for iterative possession/passing/shooting structure, the [Dixon-Coles family](https://github.com/topics/dixon-coles) for attack/defence strength thinking, and open **xG** models ([xg_modeling-with-football-data](https://github.com/finleyaf/xg_modeling-with-football-data), [Football-xG-Predictor](https://github.com/bsobkowicz1096/Football-xG-Predictor)) for shot quality.

How a block works now: each five-minute block plays 2–4 possession chains; the attacking side is weighted by possession share (midfield plus home edge), the carrier starts at their formation slot, and two to five passes/dribbles move the ball goal-ward; if the chain reaches the final third a shot is taken from its actual coordinates, with **xG from a distance/angle logistic** (≈0.42 central from 11 m, ≈0.12 from 20 m, ≈0.03 from 30 m) multiplied by the attack-vs-defence strength (tactics included). The roll decides goal/save/off-target, so goals now come from quality shots instead of a flat chance probability. Every pass, dribble, shot and restart is recorded in a **carrier timeline** (`{minute, t, side, kind, from, to, carrier, receiver, duration}`) plus per-shot xG, and the report carries `timeline`, `shotXgs`, `xg`, `shotsV2` and `engine:'v2'` into the saved match so the watch can animate a ball that belongs to a player.

Live matches run the same engine block by block, so **quick simulation and live play with the same seed still agree**, and mid-match tactic changes and substitutions re-rate the remaining blocks as before. Home advantage, stronger-attack scoring and shot-quality ordering are covered by tests.

Validation: typecheck, 527 tests — six new v2 cases (determinism and coherence; xG falling with distance and central > wide; a stronger attack scoring more and earning more xG across 80 seeds; home advantage over 120 matches; summary consistency; attack strength reacting to tactics and the opponent's defence) plus the existing v1 and live suites — four migration checks, `npm run prebuild` and a build. The watch animation from the carrier timeline is the next UI step.

## 3.74 — player condition, injuries and the assistant
